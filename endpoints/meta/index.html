    POST /judge/meta — 점수 불일치 원인 분류(펀웨이브)¶

    무엇을 판정하나 · 언제 쓰나¶

    • 기업 채점 점수와 /judge/faithfulness의 결과가 어긋난 문항 1건에 대해, 어긋난 원인을 하나로 분류함("평가 결과를 다시 평가")
    • 판정 흐름에서의 자리: ② 독립 판정 모델 단계의 뒤쪽
      • 실행기가 /judge/faithfulness 1회차 결과를 받은 뒤, vendor_meaning_assessment가 적정이 아니거나 correct_relevance가 동일상황이 아닌 문항만 1번 부름 (src/judge_api/run_judge.py:302-315)
      • 실행기 --no-meta면 부르지 않음
    • 판정 값을 바꾸지 않음 — 판정 집계가 판정 사유 문장 끝에 "불일치 원인: …"으로만 붙임 (src/report/verdict.py:321)

    경로 · 메서드¶

    • POST /judge/meta (src/judge_api/app.py:415-425)

    요청 필드¶

    • 요청 형식 정의: MetaReq (src/judge_api/app.py:234-242)
    이름 형 필수 기본값 뜻
    case_id 문자열 예 — 문항 식별자
    vendor 문자열 또는 null 아니오 "funwave" 기업 이름. 서버가 읽지 않음(받기만 함)
    source 문자열 또는 null 아니오 "" 원문
    input 문자열 또는 null 아니오 "" 통역문
    vendor_scores 객체 아니오 {} 기업 점수. 실행기는 meaning · similarity · final · terminology_score를 넣음
    judge_result 객체 아니오 {} /judge/faithfulness 결과. 실행기는 meaning_fidelity · vendor_meaning_assessment · comment_accuracy · correct_relevance · reasoning · errors_found를 넣음. 3,000자에서 잘림
    correct 문자열 또는 null 아니오 null 기업 참고 문장
    correct_relevance 문자열 또는 null 아니오 null /judge/faithfulness의 correct_relevance
    • 실행기가 만드는 요청: src/judge_api/run_judge.py:315
    • judge_result 밖의 값은 2,000자에서 잘림 (src/judge_api/app.py:417, :271-277)

    응답 필드¶

    이름 형 뜻 가능한 값
    case_id 문자열 요청의 case_id —
    judge_model 문자열 판정에 쓴 모델 이름 JUDGE_MODEL 값
    discrepancy 불 실제로 불일치가 있는가 true · false
    cause 문자열 불일치 원인 유사도 코퍼스 미스매치 · LLM 판정 흔들림 · 채점 기준 한계 · judge 오류 · 불일치 없음
    explanation 문자열 설명(한국어 2~3문장) —
    usage · latency_s · raw_key — 공통 사항 —
    • 모델 출력 형식 정의: META_SCHEMA (src/judge_api/app.py:170-179), 응답 조립 (:420-425)
    • 교차 확인(xling) 없음 — language와 무관하게 주 모델만 부름 (src/judge_api/app.py:418)
    • cause 값의 뜻 (src/judge_api/app.py:155-160)
    값 뜻
    유사도 코퍼스 미스매치 기업 참고 문장이 다른 상황 · 다른 문장이라 유사도 · 최종 점수가 왜곡됨
    LLM 판정 흔들림 기업 의미 점수 자체가 원문 기준으로 설명되지 않음(코멘트와 점수가 모순 등)
    채점 기준 한계 기준 자체가 판정 폭을 허용해 양쪽 모두 방어 가능
    judge 오류 독립 판정 모델 쪽 판정이 명백히 틀렸거나 과도함
    불일치 없음 실제로는 ±15 이내이거나 같은 결론

    예시¶

    curl -s -X POST http://127.0.0.1:8787/judge/meta \
  -H 'Content-Type: application/json' \
  -d '{
        "case_id": "DEMO-FT-002",
        "source": "이 약은 하루에 두 번, 식사 후에 드세요.",
        "input": "Take this medicine three times a day after meals.",
        "vendor_scores": {"meaning": 90, "similarity": 85, "final": 88, "terminology_score": 100},
        "judge_result": {"meaning_fidelity": 20, "vendor_meaning_assessment": "과대",
                         "comment_accuracy": "오류", "correct_relevance": "동일상황"},
        "correct": "Take this medicine twice a day after meals.",
        "correct_relevance": "동일상황"
      }'

    import asyncio, sys
sys.path.insert(0, "src")            # 저장소 최상위에서 실행
from judge_api.client import JudgeClient

payload = {
    "case_id": "DEMO-FT-002",
    "source": "이 약은 하루에 두 번, 식사 후에 드세요.",
    "input": "Take this medicine three times a day after meals.",
    "vendor_scores": {"meaning": 90, "final": 88},
    "judge_result": {"meaning_fidelity": 20, "vendor_meaning_assessment": "과대"},
    "correct_relevance": "동일상황",
}

async def main():
    c = JudgeClient()
    res = await c.meta(payload)
    print(res.get("cause"), res.get("explanation"))
    await c.aclose()

asyncio.run(main())

    판정 값 읽는 법¶

    • 판정 값(성공 · 실패 등) 없음 — 실패 · 통과를 정하지 않음
    • cause가 불일치 없음이 아니면 판정 집계가 판정 사유 끝에 "불일치 원인: cause — explanation 앞 100자"를 붙임 (src/report/verdict.py:321)
    • 판정 집계 결과 파일의 meta_cause 열에 cause가 들어감 (src/report/verdict.py:515)

    주의할 점¶

    • 판정 모델을 실제로 호출함 → 사용 한도를 씀, 요청 · 응답 전문이 raw/judge/에 남음
    • 판정 집계는 run과 case_id가 같은 meta 결과를 찾음 — 실행기는 1회차 결과에 대해서만 부르므로 문항당 1건
    • judge_result에 무엇을 넣을지는 서버가 정하지 않음(그대로 모델에 넘김). 실행기와 같은 키를 넣어야 같은 조건으로 판정됨
