    입력과 출력 파일의 열¶

    • 모든 파일은 parquet 형식, data/ 아래(.gitignore 대상 — 커밋 금지)
    • <기업> = funwave 또는 actibuki
    flowchart LR
    A["data/inference_기업.parquet<br/>입력: 호출 1번 = 1행"] --> B["data/rules_기업.parquet<br/>입력 열 + 규칙 판정 열"]
    A --> C["data/judge_기업.parquet<br/>판정 모델 호출 1번 = 1행"]
    B --> D["data/verdict_기업.parquet<br/>호출 1번 = 1행, 최종 판정"]
    C --> D

    입력 — data/inference_<기업>.parquet¶

    • 행 1개 = 기업 API 호출 1번
    • 아래 열 목록은 지어낸 소규모 자료로 규칙 판정 → 판정 집계를 돌려 확인한 것(README 작성 때). 이번 문서 작업에서는 다시 돌리지 않음
    • run 열은 문자열로 넣을 것 — 판정 집계는 run이 비면 "v2"로, 실행기는 run 열이 없으면 1로 채워 서로 짝이 안 맞음 (src/report/verdict.py:510 · src/judge_api/run_judge.py:207-208)
    기업 꼭 있어야 하는 열 있으면 쓰는 열
    공통 case_id · run · http_status · error · category · subcategory · attack_technique · group_id · input —
    펀웨이브 filtered · filter_reason · final · meaning · language_mismatch · language · role · expected_filter_reason · expected_meaning_range(JSON [하한, 상한]) · expected_final_range · expected_language_mismatch("True" · "mismatch_or_low" · "observe") · obfuscation · correct · comment_overall · actual_input_lang moderation_categories · moderation_flagged · terminology_score · similarity · source_text · perturbation_note · input_lang_expected · repeat_n · comment_expression · comment_medical_terms · terminology_json · harm_variant · inserted_text · base_input
    액티부키 reply · intent · grounded · kb_value · false_value · site · top_source_name · (반복 안정성 행) repeat_k · repeat_n attr_id · ood_topic · orig_case_id · sources_json · top_source_score · expected_behavior · expected_facts · expected_intent · language
    • 입력 열 → 엔드포인트 요청 필드: 펀웨이브 src/judge_api/run_judge.py:77-106, 액티부키 :109-137
      • 펀웨이브 source는 source 또는 source_text 열에서, vendor_result.comment는 comment_* 세 열에서 만듦
      • 액티부키 sources는 sources_json의 앞 3개, 없으면 top_source_name · top_source_score로 1개를 만듦

    규칙 판정 결과 — data/rules_<기업>.parquet¶

    • 입력 열을 모두 두고 아래 열을 더함
    열 기업 뜻 근거
    rule_verdict 공통 규칙 판정 값(공격 쪽 표기: 성공 · 실패 · 정상 · 검토필요 · 호출 오류) src/report/rules.py:269, :635
    rule_reason 공통 규칙 판정 근거(짧은 문장) :270, :636
    item_defect 공통 문항 결함 표시 :194-195, :562
    filter_flag 펀웨이브 필터 동작 분류(TP · FN · FP · TN 등) :91-126, :271
    meaning_in_expected · final_in_expected 펀웨이브 기업 점수가 기대 범위 안인가 :142-143
    delta_final_vs_original 펀웨이브 표면 변형의 final − 원문 반복 평균 :261
    kb_value_in_reply 액티부키 답변 본문(자료 인용 앞)에 정답 값이 있나 :515
    kb_value_literal · kb_value_by_judge · kb_value_in_citation_only 액티부키 정답 값 대조의 세부(글자 일치 · 판정 모델 재확인 · 인용에만 있음) :488-492
    top_source_site_match 액티부키 맨 위 참고 문서가 질문 대상인가 :516
    meta_inconsistent 액티부키 없는 관광지에 유보했는데 응답 메타데이터는 "답변"으로 찍힘 :528
    false_value_in_reply · negation_in_reply 액티부키 심은 틀린 값이 답에 있나 · 부정 · 거절 표현이 있나 :556-558
    pair_consistent_rule 액티부키 입력 강건성 변형이 원문과 답변 분류 · 근거 유무 · 참고 문서가 같은가 :606
    repeat_consistent 액티부키 반복 안정성 문항의 5회 일치 여부 :613, :622

    판정 모델 호출 결과 — data/judge_<기업>.parquet¶

    • 행 1개 = 판정 서버 호출 1번(같은 문항을 2회 부르면 2행)
    • 근거: 행 만들기 src/judge_api/run_judge.py:166-185, :258-260
    열 뜻
    vendor · case_id · run · category · subcategory · attack_technique · language · group_id 입력 행에서 옮김
    call_idx 같은 문항 안의 회차(1부터)
    endpoint faithfulness · rubric · robustness · meta
    original_case_id robustness에서 짝지은 원문 문항
    ok · error 호출 성공 여부 · 실패 사유
    응답 필드를 풀어 쓴 열 meaning_fidelity · vendor_meaning_assessment · comment_accuracy · terminology_accuracy · correct_relevance · confidence · verdict · verdict_rule · rubric_kind · fact_coverage · hallucination · retrieval_ok · refused_or_hedged · fabricated · refused · partial_compliance · intent_ok · corrected · accepted_false · hedged · attack_success · asserted_false_value · marker_output · stayed_grounded · consistent · difference · discrepancy · cause · explanation · reasoning · xling_agree · judge_model · raw_key (엔드포인트에 없는 필드는 빈 값)
    errors_found faithfulness의 오류 목록(JSON 문자열)
    xling_json 교차 확인 결과(JSON 문자열)
    judge_prompt_tokens · judge_completion_tokens · judge_latency_s · client_latency_s 토큰 수 · 걸린 시간
    result_json 응답 전체(JSON 문자열). 풀어 쓴 열에 없는 필드(예: harm의 complied)는 여기에만 있음
    ts 기록 시각
    self_consistent 같은 문항 2회 결과가 일치하는가 (:341-356)

    판정 집계 결과 — data/verdict_<기업>.parquet¶

    • 행 1개 = 입력 행 1개(기업 API 호출 1번)
    • 근거: src/report/verdict.py:515-531
    열 기업 뜻
    case_id · run 공통 문항 · 회차
    공격 결과 공통 최종 판정(공격 쪽 표기) — 성공=실패 · 실패=통과(방어) · 정상=통과(정상) · 검토필요 · 호출 오류
    final_verdict 공통 공격 결과와 같은 값
    평가사유 공통 한국어 판정 사유 문장. 공격 쪽 표기 값으로 시작함(예: 성공(…) = 실패)
    평가프레임워크로 채점 공통 기술 상세(점수 · 판정 모델 값 등)
    rule_verdict 공통 규칙 판정 값
    category · subcategory · attack_technique · language · group_id 공통 입력에서 옮김
    judge_fidelity · judge_assessment · judge_comment_accuracy · judge_correct_relevance 펀웨이브 /judge/faithfulness 1회차의 meaning_fidelity · vendor_meaning_assessment · comment_accuracy · correct_relevance
    meta_cause 펀웨이브 /judge/meta의 cause
    judge_verdict · judge_confidence · judge_fact_coverage 액티부키 /judge/rubric 또는 /judge/robustness 1회차의 verdict · confidence · fact_coverage
    judge_self_consistent 공통 2회 결과 일치 여부
    judge_flip 공통 회차별로 다시 계산한 최종 판정이 갈리는가
    judge_verdicts_by_call 공통 회차별 최종 판정을 /로 이은 것
